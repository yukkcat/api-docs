## Models

The endpoint structure is the same, but standard models and `-c` enterprise models use different request bodies:

| Model | Best for |
| --- | --- |
| `gemini-3-pro-image-preview` | Image quality |
| `gemini-3.1-flash-image-preview` | Speed; also supports `8:1` / `4:1` / `1:4` / `1:8` ultra-wide and ultra-tall ratios |
| `gemini-3-pro-image-preview-c` | Enterprise Pro; uses the native Gemini protocol and supports 4K, concurrency, and a 100% success rate |
| `gemini-3.1-flash-image-preview-c` | Enterprise Flash; uses the native Gemini protocol and supports 4K, concurrency, and a 100% success rate |

- **Standard models**: for compatibility with the current API, set dimensions under both `generationConfig.imageConfig` and `generationConfig.responseFormat.image`.
- **`-c` enterprise models**: use native Gemini passthrough and send only `generationConfig.imageConfig`; do not send the non-native `responseFormat` field.

## Parameters

| Parameter | Description |
| --- | --- |
| `imageConfig.aspectRatio` | Native Gemini aspect-ratio parameter; omit it for image-to-image requests to follow the reference image automatically |
| `imageConfig.imageSize` | Native Gemini resolution parameter: `1K` / `2K` / `4K`; the K must be uppercase |
| `responseFormat.image` | Compatibility parameter for standard models only; copy the same `aspectRatio` and `imageSize` values here, but do not send it to a `-c` model |
| `responseModalities` | `['IMAGE']` requests an image; the standard compatibility route also supports `['TEXT']` for a URL and `['IMAGE','TEXT']` for both; a native `-c` image part must be returned as `parts[].inlineData` |

> For 2K or 4K output from a standard model, send both dimension groups. Sending only `responseFormat.image` may still produce the default 1K output—for example, 896x1200 at `3:4`.

> For 2K or 4K output from a `-c` model, send only `imageConfig`. An HTTP 200 response after including `responseFormat` does not mean that this non-native field took effect.

> Do not send `aspectRatio: "auto"`. Omit `aspectRatio` to use automatic sizing.

## Supported ratios and pixels

The table shows the target pixels when aspect-ratio and resolution parameters are honored correctly. A `-c` model must pass the dimension and response-structure checks below; HTTP 200 alone is not sufficient:

| Ratio | 1K | 2K | 4K |
| --- | --- | --- | --- |
| `1:1` | 1024x1024 | 2048x2048 | 4096x4096 |
| `16:9` | 1376x768 | 2752x1536 | 5504x3072 |
| `9:16` | 768x1376 | 1536x2752 | 3072x5504 |
| `4:3` | 1200x896 | 2400x1792 | 4800x3584 |
| `3:4` | 896x1200 | 1792x2400 | 3584x4800 |
| `3:2` | 1264x848 | 2528x1696 | 5056x3392 |
| `2:3` | 848x1264 | 1696x2528 | 3392x5056 |
| `5:4` | 1152x928 | 2304x1856 | 4608x3712 |
| `4:5` | 928x1152 | 1856x2304 | 3712x4608 |
| `21:9` | 1584x672 | 3168x1344 | 6336x2688 |

Only the Flash family, `gemini-3.1-flash-image-preview` and `gemini-3.1-flash-image-preview-c`, supports ultra-wide and ultra-tall output: `8:1` = 2928x352, `4:1` = 2064x512, `1:4` = 512x2064, and `1:8` = 352x2928. Multiply each dimension by 2 or 4 for 2K or 4K.

> The model can produce strong architecture, color, and composition, but long Chinese passages may still contain missing, incorrect, or reordered characters. Add body text in a design tool after generation instead of treating long text rendered inside an image as final copy.

### Standard models: requesting 4K reliably

This non-`-c` example uses `3:4`. Keep both parameter groups identical:

```json
{
  "generationConfig": {
    "responseModalities": ["IMAGE"],
    "imageConfig": {
      "aspectRatio": "3:4",
      "imageSize": "4K"
    },
    "responseFormat": {
      "image": {
        "aspectRatio": "3:4",
        "imageSize": "4K"
      }
    }
  }
}
```

For a standard model, `3:4 + 4K` should return 3584x4800. An actual result of 896x1200 means the request was still processed as 1K.

### `-c` enterprise models: native 4K request

For a `-c` model, keep only the native Gemini `imageConfig` field. The complete request body is:

```bash
curl -X POST "https://api.klong.lat/v1beta/models/gemini-3.1-flash-image-preview-c:generateContent" \
  -H "x-goog-api-key: <API_KEY>" \
  -H "Content-Type: application/json" \
  -d '{
    "contents": [{
      "role": "user",
      "parts": [{ "text": "Your prompt" }]
    }],
    "generationConfig": {
      "responseModalities": ["IMAGE"],
      "imageConfig": {
        "aspectRatio": "3:4",
        "imageSize": "4K"
      }
    }
  }'
```

The core request body is:

```json
{
  "contents": [
    {
      "role": "user",
      "parts": [
        { "text": "Your prompt" }
      ]
    }
  ],
  "generationConfig": {
    "responseModalities": ["IMAGE"],
    "imageConfig": {
      "aspectRatio": "3:4",
      "imageSize": "4K"
    }
  }
}
```

Do not add `generationConfig.responseFormat` to a `-c` request.

A successful native response should contain an image part like this (the actual base64 data is omitted):

```json
{
  "candidates": [
    {
      "content": {
        "parts": [
          {
            "inlineData": {
              "mimeType": "image/png",
              "data": "<BASE64>"
            }
          }
        ]
      }
    }
  ]
}
```

#### Validating native `-c` routing

Do not rely on the HTTP status alone. After deployment, `3:4 + 4K` must satisfy both assertions:

1. The actual image dimensions are **3584x4800**.
2. The image is returned at `candidates[].content.parts[].inlineData`, not as a Markdown data URL inside `parts[].text`.

If the response is HTTP 200 but the image is still a landscape 1408x768 file and the response contains a Markdown data URL in `parts[].text`, the request is still reaching the old compatibility route. In that case, `imageConfig` and `responseModalities` are not being honored as native Gemini fields. Receiving HTTP 200 with or without `responseFormat` only means that the field was accepted or ignored; it does not prove that 4K took effect.

For the standard compatibility response, the image is typically returned at `candidates[0].content.parts[0].inline_data.data`. A native `-c` response must use `candidates[].content.parts[].inlineData.data`; if it returns only `parts[].text`, use the routing checks above.

### Text to image - URL

Set `responseModalities` to `["TEXT"]`. The URL is returned at `candidates[0].content.parts[1].file_data.file_uri`. Use `["IMAGE","TEXT"]` to return both base64 and a URL.

### Image to image - base64 input

Add an image part next to the text part in `parts`:

```bash
curl -X POST "https://api.klong.lat/v1beta/models/gemini-3-pro-image-preview:generateContent" \
  -H "x-goog-api-key: <API_KEY>" \
  -H "Content-Type: application/json" \
  -d '{
    "contents": [{
      "role": "user",
      "parts": [
        { "text": "Convert this to Japanese watercolor while preserving the subject and composition" },
        {
          "inline_data": {
            "mime_type": "image/png",
            "data": "<BASE64>"
          }
        }
      ]
    }],
    "generationConfig": {
      "responseModalities": ["IMAGE"]
    }
  }'
```

### Image to image - URL input

Replace `inline_data` above with:

```json
{
  "file_data": {
    "mime_type": "image/png",
    "file_uri": "https://example.com/input.png"
  }
}
```

### Follow the reference ratio at 2K

For a standard model, set only `imageSize` in both locations and omit `aspectRatio`:

```json
{
  "generationConfig": {
    "responseModalities": ["IMAGE"],
    "imageConfig": {
      "imageSize": "2K"
    },
    "responseFormat": {
      "image": { "imageSize": "2K" }
    }
  }
}
```

For a `-c` model, remove `responseFormat` and keep only `imageConfig.imageSize`.

When both `aspectRatio` and `imageSize` are omitted, the upstream service determines the reference ratio and output tier. For text-to-image requests that need a fixed shape, pass both the ratio and resolution.
